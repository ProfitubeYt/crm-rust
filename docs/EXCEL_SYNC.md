# Двусторонняя синхронизация Excel

Общая книга **«Чеки.xlsm»** получает чеки с сервера и автоматически отправляет изменения. Пользователи открывают её локальные копии на разных компьютерах; все копии используют одну серверную учётную запись **admin, id 1**, один Excel-grant и прежний UUID книги admin. Нужен настольный **Microsoft Excel для Windows с действующей лицензией и разрешёнными макросами**. Excel Web и мобильный Excel этот клиент не исполняют. Приложение TBSparcer для работы открытой книги не требуется.

## Готовая книга с сервера

**Статус.** Реализовано и покрыто тестами backend (раздел «Проверка» ниже). Ревизия `20261111_0032` входит в production-схему (на 15.11.2026 — `20261112_0035`, см. [DEPLOYMENT.md](DEPLOYMENT.md)). В настольном Excel готовый файл по этому сценарию **не открывался** и VBA не выполнялся (последняя запись: 11.11.2026).

**Причина.** Шаблон из `GET /api/excel/workbook` пуст: в `_sync` нет идентификатора книги, адреса сервера и владельца. `ExcelSync.StartSync` в такой книге сам придумывает UUID, `ConfigureSharedProfile` выходит (`Len(url) + Len(owner) = 0`), таймер не ставится и ни одного HTTP-запроса не происходит. Рабочие книги до сих пор заполнял администратор вручную. Кроме того, пароль можно было задать только книге, которая уже подключена вручную.

**Новый поток.**

1. Владелец в клиенте вводит название и пароль: `POST /api/excel/workbooks`. Сервер заводит книгу (запись пароля) и возвращает её идентификатор.
2. Клиент скачивает файл: `GET /api/excel/workbooks/{workbook_id}/file`. Файл можно скачивать сколько угодно раз, для любого компьютера: это всегда одни и те же байты.
3. На компьютере: открыть файл, разрешить макросы, ввести пароль. Книга сама вызывает `POST /api/excel/v1/activate` (пароль → grant этого компьютера), затем `GET /api/excel/v1/snapshot`. Ручной `Connect` и вставка ключа не нужны.

**Что сервер записывает в `_sync`** (и только это; сверено с `backend/tools/excel_sync/ExcelSync.bas`):

| Ячейка | Значение | Кто читает в VBA |
|---|---|---|
| `B1` | UUID книги, строчными буквами с дефисами | `StartSync`; пустую ячейку Excel заменил бы случайным UUID, неизвестным серверу |
| `B5` | адрес сервера в единственном написании (см. ниже) | `ConfigureSharedProfile`, проверка `ValidServerUrl`; сравнивается как текст с адресом в локальном состоянии |
| `B6` | пусто | прежний ключ в файле; книга ключей не содержит |
| `B7` | id владельца (текстом) | `ConfigureSharedProfile`; `CheckIdentity` сверяет его с `user_id` снимка до отправки любых изменений |
| `B8` | `1` | общий режим (`SharedProfile`): именно он заставляет книгу спросить пароль; любое другое значение останавливает `StartSync` |
| `B9` | пусто | строка состояния того, кто последним сохранял шаблон |

`B2`–`B4` и `B10` остаются как в шаблоне. Меняется одна часть архива — лист `_sync`; все остальные записи ZIP, включая `xl/vbaProject.bin`, копируются байт в байт. В файл не попадают ни пароль, ни его хеш, ни ключ (grant): функция сборки их не принимает.

**Контракт** (вход — обычная сессия приложения, вкладка «Транзакции»; для создания ещё и открытый scope транзакций):

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `POST /api/excel/workbooks` | JSON `{"name": string, "password": string, "server_url"?: string \| null}`. `name`: 1–80 символов после схлопывания пробелов, без управляющих символов. `password`: 8–128 символов, не из одних пробелов. Другие поля запрещены. | `201` `{"workbook": {"workbook_id": string, "name": string, "created_at": string, "updated_at": string, "locked_until": string \| null}, "server_url": string}`; `Cache-Control: no-store`. Времена — UTC, ISO-8601 с `Z`. `server_url` — адрес, который будет записан в файл. |
| `GET /api/excel/workbooks/{workbook_id}/file` | необязательный параметр `server_url` | `200`, тело — XLSM, `Content-Type: application/vnd.ms-excel.sheet.macroEnabled.12`, `Content-Disposition: attachment; filename*=utf-8''<имя>.xlsm` (для имён из букв ASCII, цифр и `_.-~` — `filename="<имя>.xlsm"`), `Cache-Control: no-store` |
| `GET /api/excel/activations` | — | как раньше, плюс `name` (у книг, подключённых вручную, `null`) и `created_at`; новые книги первыми |
| `PUT /api/excel/activations` | как раньше | теперь принимает и книгу, созданную здесь, до первого подключения; `name` и `created_at` сохраняются |

Отказы приходят в общем конверте ошибок приложения; код лежит в `detail.error`:

| Статус | `detail.error` | Когда |
|---|---|---|
| 422 | `workbook_name_invalid`, `password_required` | название или пароль не прошли проверку сервера |
| 422 | `invalid_server_url` | `server_url` не годится для книги или называет не этот сервер |
| 422 | — (`error_code: validation_error`, `detail` — список) | типы, длины, лишние поля, неверный UUID в пути; значения запроса в ответ не возвращаются |
| 404 | `workbook_not_found` | книги нет среди книг пользователя (в том числе чужая) |
| 409 | `too_many_excel_workbooks` | у владельца уже 20 записей паролей |
| 503 | `excel_public_url_not_configured` | нет адреса, пригодного для книги (см. ниже) |
| 503 | `excel_workbook_not_built`, `excel_workbook_template_invalid` | шаблона нет или он не тот, что ожидается |
| 403 | строка в `detail`: `scope_changed`, `inactive_user`, `user_locked`, `access_expired` | состояние владельца или scope изменилось |

При любом отказе создания запись не появляется: адрес проверяется и файл собирается до записи в базу, а запись и её строка аудита (`excel_workbook_created`) фиксируются одной транзакцией.

**Адрес сервера в файле.** Книга принимает только `https://host[:port]`, а `http` — только для `127.0.0.1` и `localhost` (правило `ValidServerUrl`); путь, параметры, имя пользователя, пробелы и не-ASCII в адресе недопустимы. Сервер пишет адрес в одном написании: строчными буквами, без порта по умолчанию и без завершающего `/`. Источник адреса:

1. `EXCEL_SYNC_PUBLIC_URL`, если задан — всегда он, что бы ни прислал клиент. Если значение непригодно, все запросы получают `503 excel_public_url_not_configured`.
2. Иначе `server_url` клиента, но только если это адрес этого же сервера: хост должен совпасть с `Host` запроса, а порт — с портом из `Host`, если он там указан (прокси может порт убрать, тогда сравнивается только хост). Так ссылка с подставленным адресом не направит книгу и вводимый в неё пароль на чужой сервер.
3. Иначе собственный адрес запроса (`scheme://host`), если он годится для книги.

Книга сравнивает адрес из `B5` с адресом в своём локальном состоянии как текст и не запускается, если они различаются («Local changes belong to another server»). Поэтому один и тот же сервер должен всегда называться одинаково; надёжнее всего задать `EXCEL_SYNC_PUBLIC_URL`.

**Владение и пароль.**

- Книга, у которой есть запись пароля, принадлежит только пользователю этой записи. Книга без записи (подключённая вручную) принадлежит пользователю, чей grant к ней привязан. Чужую книгу нельзя скачать, перепаролить или удалить: ответ `404`.
- Пароль хранится только как PBKDF2-HMAC-SHA256 с солью (200 000 итераций), как и раньше. Пять неверных попыток блокируют активацию книги на 15 минут для всех (`429 excel_activation_locked`); новый пароль блокировку снимает.
- Запись фиксирует scope и `permissions_version` владельца на момент создания. Если права или scope изменились, активация отвечает `403 permissions_changed_reset_excel_password` / `scope_changed_reset_excel_password`, пока владелец не задаст пароль заново.
- Grant, выданный паролем, привязан к компьютеру и книге, отзывается в списке подключений (`DELETE /api/excel/grants/{id}`) и учитывается в лимите 20 активных подключений. Повторная активация того же компьютера заменяет только его ключ.
- `DELETE /api/excel/activations/{workbook_id}` по-прежнему убирает пароль: новые компьютеры не активируются, активированные работают. Вместе с записью пропадает название; книга, которую ещё никто не открывал, после этого больше не существует.

**Совместимость.** Существующие пути, поля и ответы не менялись; добавлены два пути и поля `name`, `created_at`, `server_url`. Прежние гранты, ручной `Connect`, обмен общего ключа на ключ компьютера (`/v1/device`), пустой шаблон `GET /api/excel/workbook` и записи паролей без названия работают как раньше. Ответы `422` маршрутов `/api/excel/*` больше не содержат поле `input` (в нём возвращался присланный запрос вместе с паролем).

**Установка на сервере.**

1. `alembic upgrade head`: ревизия `20261111_0032` добавляет один необязательный столбец `excel_sync_activations.name`. Откат `alembic downgrade 20260923_0031` убирает только его; записи паролей и гранты остаются.
2. По желанию задать в `.env` сервера `EXCEL_SYNC_PUBLIC_URL=https://<публичный хост>`. Без него адрес берётся из запроса; за Caddy с `--proxy-headers` это тот же `https://host`, по которому подключён клиент.
3. Перезапустить backend. Шаблон и макросы не менялись, книгу пересобирать не нужно.

2. Неверный пароль должен вернуть запрос с текстом «Неверный пароль.».

**О блокировке макросов.** Файл, попавший на компьютер через браузер, почту или мессенджер, Windows помечает как полученный из интернета, и Office не выполняет в нём макросы, пока файл не разблокирован (свойства файла → «Разблокировать») или не лежит в надёжном расположении. Это обычное поведение Office, а не свойство книги; при передаче файла на другой компьютер об этом стоит предупредить. В этой сессии не проверялось.

## «Операция»: поля API транзакций и сортировка экспорта: 11.11.2026

**Статус.** Реализовано в backend, проверено тестами на SQLite и на одноразовом PostgreSQL 16 (11.11.2026).

**Что было.** Книга строит ячейку «Операция» правилом `OperationDisplay` (`ExcelSync.bas`): первая строка чека, если это заголовок банка; иначе значок и подпись по **сохранённому** типу операции, в оформлении банка — назначенного строке (`excel_bank`) или банка источника. API транзакций отдавал только тип, **выведенный** из сохранённого типа и текста чека (`transaction_type`), и не отдавал `excel_bank`. Экспорт не знал сортировки по «Операции» и молча сортировал по дате.

**Новые поля `TransactionResponse`.** Они есть в каждом ответе с транзакцией: `GET /api/transactions/` (`items[]`), `GET /api/transactions/{id}`, `POST /api/transactions/` и `transaction` в ответе обработки чека.

| Поле | Тип JSON | Значение |
|---|---|---|
| `stored_transaction_type` | `string \| null` | `transactions.transaction_type` как хранится: `DEBIT`, `CREDIT`, `CONVERSION` или `REVERSAL`. То же значение, что `records[].fields.transaction_type` снимка Excel. |
| `excel_bank` | `string \| null` | `transactions.excel_bank`: `CardXabar`, `HUMO Card` или `null`. То же значение, что `records[].fields.excel_bank` снимка Excel. |

Существующие поля не менялись: `transaction_type` остаётся выведенным типом, `transaction_type_display` — его подписью. Сервер без этого изменения новых полей не присылает; отсутствующее поле клиент должен считать отсутствующим и не подставлять в него значение другого поля.

**Сортировка экспорта.** `GET /api/transactions/export?sort_by=operation&sort_dir=asc|desc`, для обоих `layout`:

- Ключ — текст ячейки «Операция», который сам экспорт пишет в макете `client` (столбец `T`): заголовок банка из первой строки чека, иначе значок и подпись по выведенному типу в оформлении банка источника.
- Сравнение — текст в нижнем регистре, по кодовым точкам Unicode (так же сравнивает свой столбец Rust-клиент).
- Строки с равным ключом идут по дате, затем по id, по возрастанию — в обоих направлениях. Это порядок, в котором клиент получает строки, поверх которого он сортирует устойчиво.
- «№ опер.» нумеруется сверху вниз, как при любой сортировке, кроме даты по убыванию.
- Остальные значения `sort_by` работают как раньше, неизвестные — по дате. `GET /api/transactions/` по `operation` не сортирует.

**Совпадение с клиентом и с книгой.** Для строк с заголовком банка текст одинаков везде. Для строк без заголовка экспорт берёт выведенный тип и банк источника, книга — сохранённый тип и `excel_bank`. Rust-клиент сейчас берёт тип из `transaction_type`, как экспорт, а `excel_bank` учитывает сам, как только сервер начинает его присылать (поле уже есть в его модели). Поэтому у строк без заголовка с назначенным `excel_bank` — а после перехода клиента на `stored_transaction_type` и у строк, где сохранённый и выведенный типы различаются, — текст в клиенте и в экспорте разный, и в файле такие строки стоят не там, где на экране. Ячейка экспорта намеренно не менялась: в нём на выведенном типе построены и подпись, и знак, а назначенный банк не учитывается вовсе. Привести её к правилу книги — отдельное решение, меняющее содержимое выгрузки; в этой ветке оно не принято.

**Проверка.** `backend/tests/test_transaction_operation_parity.py`: оба поля рядом с прежним выведенным типом и их равенство полям снимка Excel; порядок экспорта в обоих макетах и направлениях, равные ключи, фильтры, строка с расхождением типов, прежнее поведение других ключей. **Не проверено:** сколько строк production затрагивает расхождение типов — доступа к production в этой сессии не было.

## Пароль книги и активация компьютера: 24.09.2026

Ключ подключения больше не хранится в файле. Каждый компьютер получает собственный отзывной grant, привязанный к нему; ключ лежит только в Windows Credential Manager (`TBSparcer.ExcelSync.<workbook_id>`) текущего пользователя Windows.

- **Новый компьютер.** Книга с общим профилем (`_sync!B8 = 1`, адрес в B5 и владелец в B7), у которой на этом компьютере нет ключа, показывает только лист **«Доступ»**. Листы с чеками остаются `veryHidden`, запросов к API нет. Двойной щелчок на «Доступ» открывает запрос пароля. После верного пароля `POST /api/excel/v1/activate` выдаёт grant для этого компьютера, чеки загружаются, а компьютер запоминается и больше пароль не спрашивает.
- **Копия файла на другом компьютере** снова видит только «Доступ»: ключа в файле нет, прежний `_sync!B6` очищается при открытии.
- **Сохранённый файл** всегда показывает только «Доступ», в том числе на активированном компьютере; в открытой книге чеки остаются видны.
- **Пароль задаёт владелец** в веб-панели «Синхронизация с Excel → 3. Защитите книгу паролем», по книге (не короче 8 символов). Смена пароля не отключает уже активированные компьютеры. Если пароль убрать, новые компьютеры активироваться не смогут. Каждый активированный компьютер виден в списке подключений как «ПК <имя>»; после отзыва его книга при следующей синхронизации снова закрывается листом «Доступ» и просит пароль.
- **Ранее подключённые компьютеры** остаются рабочими: при первой синхронизации их прежний ключ молча обменивается на grant этого компьютера (`POST /api/excel/v1/device`). Прежний общий grant не отзывается автоматически. Старые копии файла ещё содержат его в `_sync!B6`, поэтому отзовите его в панели, когда все компьютеры перейдут на новый клиент.
- Ошибки активации: неверный пароль — **401** `excel_activation_password_invalid`; после серии ошибок — **429** `excel_activation_locked` (новый пароль снимает блокировку); пароль не задан — **403** `excel_activation_unavailable`.

**Особенность Excel, найденная при проверке:** если изменить видимость листов внутри `Workbook_BeforeSave`, это изменение не попадает в сохранённый файл. Поэтому `ExcelSync.HandleBeforeSave` отменяет сохранение Excel, пока чеки видны, скрывает их и сохраняет книгу повторно с отключёнными событиями (для «Сохранить как» — в выбранный файл). Книгу, где виден только «Доступ», Excel сохраняет сам. Повторное сохранение изнутри `BeforeSave` работает при сохранении из интерфейса (Ctrl+S, команда `FileSave`), но COM-вызов `Workbook.Save()` его молча пропускает. Поэтому тесты сохраняют книгу через `CommandBars.ExecuteMso("FileSave")`.

Native-проверка [native_activation.ps1](../backend/tools/excel_sync/testing/native_activation.ps1) на изолированном loopback fixture прошла **6 проверок**:

- обмен прежнего ключа на ключ компьютера;
- сохранённый файл скрывает чеки;
- новый компьютер видит только «Доступ» и не обращается к API;
- неверный пароль, снятый пароль и верный пароль с загрузкой чеков;
- активированный компьютер запоминается после сохранения и переоткрытия;
- после отзыва книга снова закрывается.

Отчёт пишется в `native-activation-verification.json`. Исторический harness общего режима теперь готовит уже активированный компьютер: ключ записан в WinCred, а не в файл. Для полного прогона ему по-прежнему нужно ручное закрытие книги в интерфейсе Excel.

## Производительность опроса и ограничения

При повторном опросе API возвращает **304 без тела**, если данные и права не изменились. Клиент использует снимок в памяти и пропускает повторный JSON-разбор и слияние уже применённых данных при пустых очередях. Проверки владельца перед отправкой, обработка локальных правок, восстановление оформления и отложенных представлений продолжают выполняться. Неверный ETag, смена владельца и отзыв доступа не допускают отправку из старого кэша. Старый сервер без ETag поддерживается через обычный ответ 200.

Идентификаторы строк читаются из Excel массивами, карта UUID строится один раз на событие редактирования, оформление новых строк применяется диапазонами. В API устранён повторный обход JSON-кодировщиком; сведения для отображения результатов отправки читаются одним запросом. Свободный текст и очистка полей больше не загружают ненужные справочники. Непустые коды лица и статьи по-прежнему проверяются по текущей базе.
Оставшиеся ограничения: Excel выполняет HTTP синхронно; первое заполнение и изменившийся снимок требуют полной обработки. Сервер для каждого опроса заново проверяет доступ и строит снимок пропорционально числу записей. Проверка на текущем объёме не доказывает отсутствие задержек при десятках тысяч строк и высокой параллельной нагрузке. Синхронный ORM внутри async route и чтение актуальных справочников для непустых кодов остаются возможными направлениями следующей оптимизации. На сервере требуется увеличить запас диска. Существующий процесс TDLib и монитор запущены без обнаруженных ошибок; состояние `authorizationStateReady` текущие логи не подтверждают отдельно.
## Работа с общей книгой

Порядок работы с подготовленным частным файлом:

1. Сохраните предоставленную **«Чеки.xlsm»** на своём компьютере и откройте редактируемую локальную копию в Excel. Разрешите макросы для этой книги; если Windows блокирует скачанный файл, используйте «Свойства → Разблокировать» у самого файла.
2. Подключение запускается автоматически. Листа Control и ручного ввода адреса или токена нет. Работайте на **CardXabar**, **HUMO Card** или **«Все транзакции»**; состояние строки и действия находятся в **AX** CardXabar и общего листа, в **BE** HUMO Card.
3. Дождитесь первого успешного получения данных. Затем редактируйте разрешённые поля; неполученная впервые копия остаётся защищённой от ввода.

С 24.09.2026 на новом ПК книга сначала просит пароль владельца (см. «Пароль книги и активация компьютера»). Адрес и владелец берутся из скрытого профиля `_sync!B5`, `B7`, `B8`, а ключ этого компьютера сохраняется в `TBSparcer.ExcelSync.<workbook_id>` текущего пользователя Windows. Во всех копиях сохраняется UUID admin **`e74a3c23-82f8-4ada-8d6f-5d81ddb42ff9`**. Имена файлов могут отличаться; новая книга другого владельца не должна получать старую очередь.

**Историческое исключение до 24.09.2026:** общий Excel-токен находился в `_sync!B6` подготовленной частной книги; новый клиент очищает эту ячейку при открытии. Обладатель старой копии файла получает доступ к общим чекам с правами admin, пока общий grant не отозван в панели. Публичный master, исходники, сборочные файлы и отчёты остаются без ключей. Сервер по-прежнему требует grant; анонимная запись не открывается, отдельные пользователи и JWT-сессии для копий не создаются. В аудит изменения всех копий попадут как действия admin, id 1.

Общая связь **бессрочная и отзывная**: `expires_at = null`, выдача с `expires_in_days = null` разрешена только действующему admin после проверки пользователя. Обычные подключения сохраняют срок 90 дней по умолчанию и числовой предел 365 дней. Лимит 20 активных подключений включает бессрочные. Отзыв, блокировка пользователя/системы, изменение версии прав, scope, источников, папок и ограничений дат продолжают действовать; бессрочность их не отменяет. После отзыва или несовместимого изменения прав администратору потребуется подготовить обновлённое подключение. Старый ключ CSV/Power Query права записи не даёт.

## Что можно редактировать

На каждом из трёх видимых листов поддерживаются **17 редактируемых полей**. Вместе с `excel_bank` протокол содержит **18 канонических полей**. Ячейки с отдельным вводом банка нет: новый чек на банковском листе получает его банк, а на общем листе сохраняет NULL. Существующий чек относится к явно заданному `excel_bank`; при пустом значении используется `metadata.source_display`: содержащий HUMO без учёта регистра — HUMO Card, остальные — CardXabar. Поэтому новый ручной чек общего листа также появляется в CardXabar; правка существующего HUMO-чека через общий лист его банк не меняет. Столбец **S** сохраняет название исходного источника. Пустое значение очищает допустимое пустое поле; неотредактированные поля сохраняются.

| Поле в книге | Поле API | CardXabar / Все транзакции | HUMO Card |
|---|---|---|---|
| Дата и время | `transaction_date` | Q | Q |
| Тип операции | `transaction_type` | T | T |
| Оператор / продавец | `operator_raw` | U | U |
| Приложение | `application_mapped` | W | W |
| Сумма | `amount` | Z | AF |
| Остаток | `balance_after` | AG | AN |
| Последние четыре цифры карты | `card_last_4` | AH | AO |
| Признак P2P | `is_p2p` | AI | AP |
| Подтверждение P2P | `p2p_confirmed` | AJ | AQ |
| Подробности | `annotation_details` | AK | AR |
| Лицо, код справочника | `annotation_person_code` | AL | AS |
| Период | `annotation_period` | AM | AT |
| Статья, код справочника | `annotation_article_code` | AN | AU |
| Валюта | `currency` | AO | AV |
| Получатель | `receiver_name` | AP | AW |
| Карта получателя | `receiver_card` | AQ | AX |
| Исходный текст чека | `raw_message` | AR | AY |

`p2p_confirmed` независим от `is_p2p`: пустая ячейка означает **null**, `0` — false, `1` — true. Изменение одного признака сохраняет значение другого. Статья показывается как **код=название**; при правке в очередь и на сервер передаётся её код. Дата операции — местное время `Asia/Tashkent`, период — месяц. Текстовые поля сохраняют Unicode и ведущие нули.

В **T** показывается подходящий исходный заголовок банковского сообщения с его символами; при отсутствии такого заголовка подпись формируется из типа операции и банка. Канонический тип остаётся `DEBIT`, `CREDIT`, `CONVERSION` или `REVERSAL`. Для изменения типа выбирают одно из этих значений. Повторная вставка неизменённой отображаемой подписи сохраняет исходный тип и не создаёт операцию обмена.

Исходные строки суммы находятся в **Y** всех трёх листов, строки остатка — в **AF** CardXabar и «Все транзакции», в **AG** HUMO Card. Числовые суммы и остатки сохраняют **копейки**, включая знак остатка; числовая сумма в таблице показывается по модулю, а её канонический знак соответствует типу операции. Сохранён исходный формат отображения целых сумм из банковского образца: округление для просмотра не изменяет числовое значение ячейки и данные сервера.

`id`, `uuid`, `version`, сведения об исходном чате/сообщении и парсере доступны только для чтения. Идентификаторы находятся в скрытых защищённых столбцах **AY:BA** CardXabar и «Все транзакции», в **BF:BH** HUMO Card и передаются строками, чтобы Excel не округлял большие числа. Служебные столбцы и вычисляемые копии полей защищены от редактирования.

Новый чек создаётся как `MANUAL`, источник `0`. Оператору требуется разрешение на этот источник. Изменением ячейки нельзя присвоить ручному чеку чужой Telegram-источник. Существующие чеки доступны в пределах актуальных прав, разрешённых дат и незакрытых периодов; исключения из блокировки периода учитываются.

## Ввод и действия в общей книге

Новый чек начните в **пустой строке сразу под чеками выбранного листа**. Данные CardXabar и «Все транзакции» начинаются со строки **5**, HUMO Card — со строки **4**. После первого ввода строка становится локальным черновиком: банковский лист задаёт свой банк, общий оставляет `excel_bank = null`. Команда добавления остаётся на строке ввода выбранного представления. Для отправки нужны дата и время, тип операции, оператор, ненулевая сумма, валюта и последние четыре цифры карты. Черновик получает текущую дату, тип `DEBIT` и валюту `UZS` по умолчанию; проверьте их перед заполнением остальных полей. Пока обязательные поля не заполнены, создания на сервере нет. Готовый черновик отправляется автоматически, без отдельной кнопки «Создать».

| Действие | Результат |
|---|---|
| Изменить разрешённую ячейку | Сохранить правку локально и запланировать отправку |
| Заполнить новую строку | Сохранить черновик; отправить создание после заполнения обязательных полей |
| Дважды нажать AX в CardXabar / Все транзакции или BE в HUMO Card у обычной строки | После подтверждения удалить чек; локальный черновик удаляется только на этом ПК |
| Дважды нажать AX / BE со статусом «Требует внимания» | Открыть решение конфликта или объяснение отказа |

Обычные изменения ячеек сохраняются локально сразу; отправка планируется через **5 секунд после ввода**. Новые серверные данные проверяются каждые **60 секунд**. Занятый Excel может задержать таймер. Книга сохраняется автоматически при изменении данных после обмена и перед закрытием; неизменный опрос не переписывает файл. Ошибка сохранения оставляет её открытой. При закрытой книге обмен останавливается; при следующем открытии на том же ПК очередь восстанавливается. Сохранённая книга защищена от ввода без макросов, чтобы изменения не прошли мимо очереди.

## Конфликты и работа без сети

Сервер сравнивает исходные и текущие значения каждого изменённого поля. При конфликте ни одна часть этой правки не применяется. Двойной щелчок по **AX** CardXabar или «Все транзакции», по **BE** HUMO Card предлагает: **Да** — повторить свои изменённые поля относительно свежих серверных значений; **Нет** — принять серверные значения; **Отмена** — оставить конфликт. Если чек удалён или доступ закрыт, можно явно отбросить оставшиеся локальные изменения. Заведомо отклонённый новый чек можно вернуть в черновик; после исправления поля он снова отправится автоматически. Неопределённый результат создания сохраняет прежний ID операции.

Снимок, намерения пользователя, конфликты и очередь хранятся в `%LOCALAPPDATA%\TBSparcer\ExcelSync\<workbook_id>\state.json`. Запись выполняется через временный файл и атомарную замену; ошибка сохранения не подменяет очередь пустой. Эти локальные данные содержат чеки и несохранённые на сервере правки. Состояние изолировано по ПК и пользователю Windows: **копирование `.xlsm` не переносит неотправленную очередь**. Сначала дождитесь отправки правок на исходном ПК; `state.json` и незавершённые операции между компьютерами не копируйте. Новая копия получает актуальные записи с сервера. Одновременно открывать две копии с этим UUID в одном профиле Windows мешает локальная блокировка.

До первого запроса операция получает неизменяемый `operation_id`. Сервер записывает изменение и результат операции одной транзакцией; уникальность `(user_id, workbook_id, operation_id)` предотвращает повторное применение при потере ответа и даже после замены токена у той же книги и того же пользователя. Повтор проверяет текущий доступ к записи. При неопределённом результате сохраняйте очередь и подключайте ту же книгу: повторное ручное создание с новым ID считается отдельной операцией.

Перед любым POST книга сначала получает `GET /api/excel/v1/snapshot` и проверяет владельца по строковому `user_id` одновременно с общим профилем и локальным состоянием. Один токен и адрес закрепляются на весь цикл GET/POST/GET, поэтому внешняя замена записи WinCred между запросами не подменяет проверенного владельца. Токен другого пользователя не может отправить сохранённую очередь прежнего владельца: обмен блокируется. Это сохраняет защиту от дублей при смене токена после потерянного подтверждения создания. Для другого пользователя нужна отдельная новая книга.

Снимок по умолчанию ограничен **50 000 строк** (`EXCEL_SYNC_MAX_ROWS`). При превышении сервер возвращает **HTTP 413**, без частичного снимка; книга сохраняет локальные изменения. Значение лимита на сервере допускается в пределах 1–200 000.

## Сборка и поставка

Команды выполняются из корня проекта на Windows:

```powershell
& .\backend\.venv\Scripts\python.exe backend/tools/build_sync_workbook.py --out backend/assets/excel_sync_template.xlsm
```

По умолчанию сборщик упаковывает исходники VBA через закреплённую **EPPlus 4.5.3.3, LGPL-3.0**. Excel для этой упаковки не запускается. Общий шаблон не содержит токена, подключения, чеков или заранее назначенного ID книги. Сборочная зависимость EPPlus и сведения о её лицензии должны сохраняться при распространении сборочных инструментов.

Дополнительный путь на машине с лицензированным Excel и уже разрешённым доступом к VBA-проекту:

```powershell
& .\backend\.venv\Scripts\python.exe backend/tools/build_sync_workbook.py --probe
& .\backend\.venv\Scripts\python.exe backend/tools/build_sync_workbook.py --native --out backend/assets/excel_sync_template.xlsm
```

`--prepare-only --out <путь>.xlsx` создаёт оболочку для последующего импорта модулей VBA. Для работы клиента нужно закончить импорт, подключить события `ThisWorkbook` и сохранить `.xlsm`.

Сборщик создаёт **девять листов с тремя видимыми представлениями**. «Все транзакции» использует столбцы и стили CardXabar; скрытое ядро называется `_transactions`, `_sync!B3` указывает на него. Новая очередь или дополнительная серверная запись для общего листа не создаются.

Для трёх представлений нужны совместимый backend **1.7.9**, схема **`20260915_0030`** и обновлённые `backend/assets/excel_sync_template.xlsm` и manifest. Добавление общего листа меняет клиентские артефакты и не требует новой миграции. Поставка **1.7.11** обновила эти два публичных файла без перезапуска; работающий backend остался 1.7.9, image 1.7.11 подготовлен для будущего пересоздания. Секретный профиль и частные чеки в публичные артефакты не входят.

Миграция 0030 поверх `20260910_0029` добавила nullable-поля `excel_bank` и `p2p_confirmed` без DEFAULT и backfill; ограничение банка допускает только `CardXabar`, `HUMO Card` или NULL. Имя общего листа не является значением банка. Миграция 0028 создала `excel_sync_grants` и `excel_sync_operations`, 0029 разрешила NULL в сроке действия grant. Бессрочный общий профиль администратор готовит отдельно только в частном пользовательском файле; скачать публичный master недостаточно для автоматического подключения.

Production-сервер обслуживает только API. Управление книгами и подключениями (grant) находится в настольном Rust-клиенте. Пользователям готовой общей книги эта панель не требуется.

### Получение публичного шаблона

Авторизованная панель скачивает готовый файл через **`GET /api/excel/workbook`**. Пока артефакт не установлен, endpoint возвращает 503. Управление подключениями использует `/api/excel/grants`; сами книги — только `/api/excel/v1/snapshot` и `/api/excel/v1/sync`. Исключение из system/launch-заголовков действует только для двух точных протокольных путей, где проверяется Excel-токен.

## Воспроизведение проверки в настольном Excel

Нужны лицензированный Excel для Windows, разрешённые макросы в отдельной тестовой копии и свободный порт `8767`. Команды выполняются из корня проекта. Пример присоединения через `Marshal.GetActiveObject` ниже предназначен только для **Windows PowerShell 5.1**: этого метода нет в стандартном .NET-хосте PowerShell 7. В подтверждённом прогоне на **PowerShell 7.6.5** вызывающий worker сам владел созданным через `New-Object -ComObject Excel.Application` экземпляром и передавал harness готовый COM-объект книги. Сам harness не создаёт Excel. Fixture создаёт новую SQLite в памяти и двух синтетических пользователей; обычный backend, его lifespan, `.env`, реальная БД и внешние уведомления не используются.

### Пароль и активация компьютера: native-проверка

Сценарию нужна свежая копия master в `TestRoot` и запущенный fixture на `8767`. Он сам вызывает `Initialize-ExcelSyncTestClient`, задаёт пароль через API владельца и в конце удаляет свой ключ из WinCred.

```powershell
& .\backend\tools\excel_sync\testing\native_activation.ps1 -Workbook $testBook -FixturePath $fixturePath -TestRoot $testRoot
```

Перед COM-вызовом `Close` сценарий вызывает `ExcelSync.StopSync`. Иначе `BeforeClose` запускает вложенное сохранение, Excel его отменяет, и скрытый экземпляр зависает на окне «Книга остаётся открытой».

### Три представления: native-проверки

Новый [native_all_view.ps1](../backend/tools/excel_sync/testing/native_all_view.ps1) запускается на отдельной копии master с девятью листами, `_sync!B3 = _transactions` и уже подготовленной синтетической сессией. Ему нужно не менее шести записей; завершённый прогон использовал fixture с 20 исходными записями. Сценарий не открывает и не закрывает Excel, использует переданные `-Workbook` и `-Session` и завершает `StopSync`.

```powershell
& .\backend\tools\excel_sync\testing\native_all_view.ps1 -Workbook $testBook -Session $nativeSession
```

Результат — **9 проверок PASSED**, `native-all-view-verification.json`: 17 полей общего листа в обе стороны, копейки и Unicode, независимые P2P/подтверждение, неизменный заголовок T без операции, сохранение HUMO при правке через общий лист, правки из банков в общий лист, создание с NULL-банком ровно один раз, отложенное удаление с восстановлением UUID и нескольких выделений, сортировка без изменения порядка банков, два неизменных опроса с проверкой Saved/SHA256/времени файла. Дополнительно проверяются полный набор UUID в общем листе и тот же набор в объединении двух банков.

### Регрессионные сценарии банковских листов

Используйте отдельную копию нового банковского master и fixture с **не менее 12 синтетическими записями** (`test_server.py --seed-count 12`). Все три сценария принимают `-Workbook` и `-Session`, используют уже инициализированную сессию владельца `1` и текущий loopback fixture. Перед прогоном очередь и конфликты должны быть пустыми. Не передавайте им пользовательскую книгу или production-подключение. Владельцем Excel остаётся вызывающий worker; сценарии завершают свой обмен и оставляют остальные открытые книги без изменений, используя существующую тестовую сессию.

```powershell
$nativeExcel = $testBook.Application
$nativeBookPath = [string]$testBook.FullName
& .\backend\tools\excel_sync\testing\native_bank_fields.ps1 -Workbook $testBook -Session $nativeSession
& .\backend\tools\excel_sync\testing\native_bank_viewport.ps1 -Workbook $testBook -Session $nativeSession
$testBook = @($nativeExcel.Workbooks | Where-Object { [string]$_.FullName -ceq $nativeBookPath })[0]
& .\backend\tools\excel_sync\testing\native_bank_edges.ps1 -Workbook $testBook -Session $nativeSession
$testBook = @($nativeExcel.Workbooks | Where-Object { [string]$_.FullName -ceq $nativeBookPath })[0]
```

[native_bank_fields.ps1](../backend/tools/excel_sync/testing/native_bank_fields.ps1) проверяет все 17 полей обоих листов, nullable-подтверждение независимо от P2P, обратное преобразование статьи, исходный числовой формат при сохранении копеек и неявный банк новых черновиков. Результат — **8 проверок PASSED**, `native-bank-fields-verification.json`.

[native_bank_viewport.ps1](../backend/tools/excel_sync/testing/native_bank_viewport.ps1) проверяет неизменные опросы обоих листов, Saved и сохранённый файл, несколько выделений, скрытые строки, масштаб и панели, удаление выше выделения, отложенную перестройку неактивного листа, offline-правку с фактическим закрытием/переоткрытием и повтор создания после потерянного ACK. Результат — **10 проверок PASSED**, `native-bank-viewport-verification.json`.

[native_bank_edges.ps1](../backend/tools/excel_sync/testing/native_bank_edges.ps1) проверяет отсутствие HTTP и сохранение просмотра при копировании, восстановление UUID черновика после подтверждения на неактивном HUMO и фактического закрытия/переоткрытия до его активации, сортировку с сохранением выбранного чека и неизменность созданной самим сценарием посторонней книги с одноимённым листом. Результат — **3 проверки PASSED**, `native-bank-edges-verification.json`. После viewport и edges прежний COM-объект закрытой книги следует заменить объектом повторно открытой копии из `Workbooks`. Результаты этих трёх полных прогонов относятся к предшествующей поставке банковского клиента; новый общий лист проверен отдельным native_all_view. Историческое ограничение ниже относится к ещё более раннему клиенту и способу вызова.

### Harness общего режима и регрессионный прогон

Для проверки **общего режима 10.09.2026** использовался [run_native_shared_e2e.ps1](../backend/tools/excel_sync/testing/run_native_shared_e2e.ps1). Он требует свежей пустой тестовой копии соответствующего master и непривязанного grant синтетического владельца `1`. Команда запуска приведена после подготовки fixture и COM-объекта ниже. Следующие примеры и результаты сохраняют условия тех прогонов; пример с двумя записями не подходит для новых bank-сценариев.

Harness проверяет импорт профиля настоящим `Workbook_Open` при отсутствующих state и WinCred, первый GET без POST, правку ячеек, неполный черновик и автоматическое создание, потерянный ACK без дубля, восстановление очереди после закрытия/открытия без сети и конфликт. В фазе **`awaiting_native_ui_close`** вызывающий должен закрыть **только указанную тестовую книгу через интерфейс Excel** в течение 180 секунд; harness сам не отправляет нажатия в окна. Он проверяет сохранённый XLSM и вновь открывает эту копию в том же Excel. После прогона заново получите её COM-объект из `Workbooks` по пути/имени сессии. Результат самого harness — `native-shared-e2e-verification.json`.

**Историческое ограничение COM-тестирования 10.09.2026 на Excel 16:** вызовы `.Close($false)` и `.Close()` приводили к отказу вложенного `ThisWorkbook.Save` внутри `BeforeClose`; новая правка не попадала в OOXML на диске. Закрытие той же тестовой книги через настоящий интерфейс (**Alt+F4**) прошло успешно. До повторного открытия независимая проверка закрытого XLSM подтвердила точный новый текст ячейки. Поэтому тот shared-сценарий использовал реальное пользовательское закрытие. Проверки сохранения и файла на диске остаются обязательными, ошибка не подавляется.

```powershell
if (Get-NetTCPConnection -State Listen -LocalPort 8767 -ErrorAction SilentlyContinue) {
    throw 'Порт 8767 занят: не подключайте тест к неизвестному серверу.'
}
$nativeTestRoot = Join-Path 'C:\Dev\tmp' ('parcer-excel-e2e-' + [guid]::NewGuid().ToString('N'))
$fixtureRoot = Join-Path 'C:\Dev\tmp' ('parcer-excel-native-api-' + [guid]::NewGuid().ToString('N'))
$serverState = Join-Path $fixtureRoot 'state'
New-Item -ItemType Directory -Path $nativeTestRoot, $fixtureRoot -ErrorAction Stop | Out-Null
$env:PYTHON_DOTENV_DISABLED = '1'
$env:DATABASE_URL = 'sqlite://'
$fixtureProcess = Start-Process -FilePath '.\backend\.venv\Scripts\python.exe' `
    -ArgumentList @('-u', 'backend/tools/excel_sync/test_server.py', '--state-dir', ('"' + $serverState + '"'), '--port', '8767') `
    -WindowStyle Hidden -PassThru `
    -RedirectStandardOutput (Join-Path $fixtureRoot 'server.stdout.log') `
    -RedirectStandardError (Join-Path $fixtureRoot 'server.stderr.log')
```

Дождитесь появления `$serverState\service.json` и ответа `GET http://127.0.0.1:8767/__test__/state` с `synthetic: true`. Начальное состояние: два чека с ID `1` и `2`, ноль операций и записей аудита. В `$serverState\credentials.json` находятся только адрес и тестовый токен с метаданными fixture; не выводите токен в журнал и не добавляйте этот файл в репозиторий. Начальный grant ещё не привязан к книге. Для нового полного прогона запускайте новый fixture: предыдущий прогон меняет данные и привязывает grant. Пути в примере соответствуют явным ограничениям lifecycle-сценария на тестовые каталоги `C:\Dev\tmp\parcer-excel-e2e-*` и `C:\Dev\tmp\parcer-excel-native-api-<32hex>\state`.

Скопируйте актуальный master в `$nativeTestRoot\native-test.xlsm`, откройте эту копию обычным способом и разрешите её макросы. Harness присоединяется к уже открытому Excel, не создаёт и не закрывает экземпляр приложения. Он назначает тестовой копии новый `workbook_id`, проверяет её расположение внутри `TestRoot` и работает только с `127.0.0.1:8767`.

```powershell
Copy-Item -LiteralPath '.\backend\assets\excel_sync_template.xlsm' -Destination (Join-Path $nativeTestRoot 'native-test.xlsm')
```

После открытия копии следующую привязку выполняйте **только в Windows PowerShell 5.1**. В worker на PowerShell 7 используйте уже принадлежащие вызывающему `$book` и `$excel`, задайте `$testBook = $book` и пропустите этот блок.

```powershell
if ($PSVersionTable.PSEdition -ne 'Desktop') {
    throw 'Этот блок требует Windows PowerShell 5.1; в PowerShell 7 передайте готовый COM-объект книги.'
}
$excel = [Runtime.InteropServices.Marshal]::GetActiveObject('Excel.Application')
$testBook = $excel.Workbooks.Item('native-test.xlsm')
```

Когда `$testBook` указывает на открытую тестовую копию, запустите **общий режим** в том же процессе PowerShell:

```powershell
& .\backend\tools\excel_sync\testing\run_native_shared_e2e.ps1 `
    -Workbook $testBook -FixturePath (Join-Path $serverState 'credentials.json') -TestRoot $nativeTestRoot
```

Следующие команды относятся к **отдельному регрессионному прогону прежнего клиента**. Для него подготовьте другой свежий fixture и тестовую копию; не запускайте второй полный harness поверх уже использованного grant общей книги:

```powershell
& .\backend\tools\excel_sync\testing\run_native_e2e.ps1 `
    -Workbook $testBook -FixturePath (Join-Path $serverState 'credentials.json') -TestRoot $nativeTestRoot
```

Отчёт `native-e2e-verification.json` содержит результат семи сценариев и путь к файлу тестовой сессии. Это регрессия протокола и очереди прежнего клиента: сценарии создания/удаления в harness начинают с подготовленного намерения и не доказывают новый ввод пустой строки или общий bootstrap. В конце harness оставляет конфликт чека `1`. В тестовой книге прежнего клиента его диалог открывался двойным щелчком по AX; создание из пустой строки и подтверждение удаления проверялись отдельно.

Отдельный прогон `native_all_fields.ps1` меняет синтетический чек `2`: все 16 полей в обе стороны, Unicode/emoji, ведущие нули, даты, копейки, очистку допустимых пустых полей и сортировку с сохранением идентификаторов. Чек `1` и его текущее состояние сохраняются. Проверяйте `passed` и отдельные результаты в его отчёте. Проверка ввода вычисляемой формулы через диалог изменения ячейки не входит именно в этот harness: `formula_validation.included_in_this_run` равен `false`. Она отдельно пройдена через реальный интерфейс и отражена в `native-ui-verification.json`; буквальный текст с начальным `=` проверяется также в all-fields-прогоне.

```powershell
$nativeReport = Get-Content -LiteralPath (Join-Path $nativeTestRoot 'native-e2e-verification.json') -Raw -Encoding UTF8 | ConvertFrom-Json
$nativeSession = Get-Content -LiteralPath $nativeReport.session_path -Raw -Encoding UTF8 | ConvertFrom-Json
& .\backend\tools\excel_sync\testing\native_all_fields.ps1 -Workbook $testBook -Session $nativeSession
```

Прежняя проверка смены ключей и сохранения/закрытия/открытия находится в [native_auth_lifecycle.ps1](../backend/tools/excel_sync/testing/native_auth_lifecycle.ps1). Её исторический успешный результат относится к прежней версии клиента; для воспроизведения общего режима 10.09.2026 использовалось UI-закрытие через handoff описанного выше shared-harness. Текущие банковские сценарии приведены отдельно выше. Для отдельной регрессии сначала завершите предыдущие UI-проверки и очистите очередь и конфликты обычной синхронизацией. Сценарий требует синтетического владельца `1`. Запускайте его через dot-source в том же worker: параметры не объявлены, он использует `$book`, `$excel`, `$session` и `$directory` вызывающего scope. Сценарий закрывает и вновь открывает только тестовую книгу, обновляя `$book`; экземпляр Excel остаётся у вызывающего процесса.

```powershell
Import-Module .\backend\tools\excel_sync\testing\native_fixture.psm1 -Force
$book = $testBook
$excel = $book.Application
$session = $nativeSession
$directory = $nativeTestRoot
. .\backend\tools\excel_sync\testing\native_auth_lifecycle.ps1
$testBook = $book
$nativeSession = $session
```

Результат записывается в `$nativeTestRoot\native-auth-lifecycle-verification.json`. Успешный прогон содержит `passed: true`, `phase: complete` и пять проверок. Он восстанавливает корректного владельца, отправляет исходную отложенную операцию ровно один раз и удаляет только созданный им синтетический чек.

Для управляемого изменения состояния тестового сервера используются следующие endpoint-ы. Они принимают только loopback-подключения и отсутствуют в приложении: их объявляет исключительно `tools/excel_sync/test_server.py`.

| Запрос | Назначение |
|---|---|
| `GET /__test__/state` | Синтетические записи, счётчики, операции, запросы и faults; сохраняет `$serverState\state.json` |
| `POST /__test__/server-edit` с `{"id":1,"fields":{"annotation_details":"server change"}}` | Независимая серверная правка через настоящий сервис и аудит |
| `DELETE /__test__/record/1` | Явное серверное удаление с tombstone |
| `POST /__test__/fault` с `{"offline":true}` / `{"offline":false}` | HTTP 503 до обработки протокольных запросов; БД и квитанции сохраняются |
| `POST /__test__/fault` с `{"fail_next_snapshot":1}` или `{"fail_next_sync":1}` | Разовый отказ до обработки запроса |
| `POST /__test__/fault` с `{"lose_next_sync_ack":true}` | Следующий успешный sync сначала фиксируется, затем ответ заменяется HTTP 503 ровно один раз |
| `POST /__test__/grant` с `{"owner_id":1,"revoke_previous":false}` | Новый непривязанный grant того же пользователя; ответ содержит путь к отдельному файлу тестового токена |
| Тот же запрос с `"owner_id":2` | Grant другого синтетического пользователя для проверки запрета смены владельца |

Имитация потери подтверждения использует HTTP 503 после commit, а не физический разрыв TCP. Offline-режим также сохраняет процесс и его БД; остановка fixture уничтожает SQLite в памяти. Поэтому весь lifecycle-прогон выполняется при работающем fixture. В shared-прогоне 10.09.2026 доказательство сохранения включало проверку OOXML **после реального UI-закрытия и до открытия**: одна лишь восстановленная из sidecar очередь не доказывает запись XLSM. Ветка отказа сохранения проверяется отдельно.

После проверки сохраните отчёты, вызовите `Remove-ExcelSyncTestClient` из `testing/native_fixture.psm1` с этой тестовой книгой и сессией: функция остановит обмен и удалит только её тестовую запись Credential Manager и её локальное состояние. Затем закройте тестовую копию и остановите **PID из `$serverState\service.json`**; PID запускающего `.venv\Scripts\python.exe` может отличаться от PID слушающего дочернего процесса. Поставляемый master не должен сохранять тестовый ID, ключ или синтетические записи.
